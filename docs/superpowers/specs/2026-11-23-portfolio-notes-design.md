## Intent and first release

One fast public site introduces Angad, presents his work and music, and gives readers a direct route to interview prep and the Notes library. A recruiter can reach work and the résumé immediately. A reader can land directly on a lesson, find a related topic, or search without an account. Music visitors can play an approved release and read its credits.

The first release includes Home, Projects, a web résumé and downloadable PDF, Music, Movies, Blog, Interesting Stuff, Notes and Interview. Release pages require approved media and facts. If an editorial section has no approved entries, show a clean index with an honest empty state. Publication requires the approved introduction, résumé/PDF, selected work, and a canonical hostname decision. The recommended release includes one playable approved music release and a custom domain. If either is unavailable, Angad may separately authorize launch with an honest Music index or a Pages hostname. Build the Interview landing from approved Notes metadata and feature only published entries with valid links. If metadata yields no curated items, link to the existing Interview collection where available, or to the library with a brief explanation. Completing the LeetCode platform, the first verified lesson, the remaining curriculum, and private progress are independent milestones.

No public accounts, visitor progress tracking, backend rendering of public pages, parallel public Notes site, or web editor for the first release. Notes remains the archive and publishing source of truth.

## Approaches

| Approach | Tradeoff |
| --- | --- |
| **One static Astro site with React where needed, built by GitHub Actions for Cloudflare Pages Direct Upload** | Selected. One domain, one navigation and index, and one verified deploy. Requires a clear contract between the Notes publisher and portfolio routes. |
| Two independent builds behind one hostname | Lower upfront UI transfer, but adds routing, duplicate navigation and search coordination, and two releases that can drift. |
| Static Next.js or a React-only public app | Static hosting remains possible. Requires rebuilding more of the existing content and route integration without improving the approved interactions. |

## File-size requirement

Every non-test text file in the new codebase has a hard maximum of **500 physical lines**. Apply this to all Portfolio work and to new, imported or changed files in the Notes publishing and curriculum work. Count blank lines, comments and a final line without a newline. The only exemption is a test file. A test-directory name alone does not exempt helpers, snapshots, fixtures, configuration, documentation, lockfiles or content. Binary assets have no text line count. Installed dependencies and transient build output live outside the versioned source inventory.

Run the check after formatting, locally and in required CI. Report the path and measured count for every failure. Split large files along meaningful module, lesson or data boundaries. Preserve human-readable formatting. Inventory untouched historical archive files separately so the integration never rewrites original sources to satisfy a new-code rule.

## Automatic CI/CD

GitHub Actions runs verification when a pull request opens, reopens or receives new commits in either repository. Require a successful check on the current revision before merge. Both gates enforce the 500-line limit after formatting. Notes verifies the source and export contract. Portfolio verifies the combined static build, browser behavior, route parity and artifact budgets.

After the initial authorized cutover, a push to Portfolio’s protected `main` or a verified change on the protected Notes publication branch automatically starts a production build. Portfolio resolves both approved revisions, verifies the final artifact, deploys those exact bytes to Cloudflare, smoke-tests the live host and records the release receipt. Routine eligible releases require no manual dispatch or per-release approval. A failed check blocks upload. A failed post-upload smoke test invokes the rollback procedure approved at cutover.

## Publishing contract

1. Pin the initial design and compatibility baseline to Notes commit `fc304f38e9757064537c094a4fb71c6447946920`. Production eligibility is separate. The initial production input must be a reviewed revision reachable from the designated Notes publication branch with passing validation on that exact SHA. Until then use the reviewed baseline for nonproduction work only. Never feed the parked local diff or an arbitrary pull request revision into production.
2. Use a clean temporary Notes checkout in CI and run its locked, trusted toolchain there. Publishable output crosses the repository boundary as a versioned snapshot with source SHA, schema version, canonical and alias routes, anchors, document and organization metadata, sanitized reader bodies, approved asset inventory, content digests and verified curriculum eligibility. Keep generated paths private unless explicitly listed for deployment. Oversized resources follow the existing original-source link policy. Validate schema compatibility, hashes, route ownership and public asset inventory before rendering. The portfolio owns canonical origin, sitemap and indexing across the combined output.
3. A successful approved Notes branch verification dispatches a rebuild with the full SHA. The portfolio validates the SHA against the designated ref and successful trusted workflow, uses an explicit pin for that run, and records both repos' SHAs, artifact digest and provenance. Configure a narrowly scoped dispatch credential only when authorized. Manual retries use the same verification. Portfolio changes and recovery builds resolve the current approved Notes revision through the same policy or an explicitly selected eligible rollback revision. Serialize production uploads and recheck revision eligibility and freshness before upload to prevent a slower prior run overriding fresher output. An authorized rollback is an explicit exception.
4. Preview and pull request workflows build without production credentials. Production publishes the exact verified artifact using Wrangler to Cloudflare Pages Direct Upload. A failed import, route collision, search check or hosting limit preserves the previous successful deployment. For a release that introduces trace packages, bind the Worker asset digest to the Pages digest in the same receipt. Record the previous good artifact and both inputs to support rollback. Keep draft lesson routes, payloads and search entries outside the production artifact.

Separate development and production credentials. Keep local copies outside Git with directory permissions `700` and file permissions `600`. Bitwarden is the backup and only Angad uses the vault CLI. Put CI and runtime values in the applicable GitHub or Cloudflare secret store. Use scoped access and short lifetimes where available. Secret values stay outside logs, command arguments, client bundles and artifacts. The later admin API verifies a signed owner session for every request and scopes reads/writes to Angad. Use stable lesson IDs and keep progress out of public builds, indexes and cache.
